## 2. 目标与范围

保留 FastAPI、SQLAlchemy、SQLite、原生 JavaScript、ECharts 和单服务部署方式，按职责渐进调整。重构目标是让依赖明确、资源可回收、配置与实际行为一致，并能用隔离测试验证关键流程。

本轮重构覆盖应用装配、采集、告警通知、分析、配置、存储、API 和前端组织。数据库产品替换、前端框架迁移、微服务拆分、新增行情供应商及新的业务功能不属于本计划。

### 2.1 兼容要求

- 保留现有公开 API 路径和已有响应字段；需要改变状态码、参数或响应语义时，先列出具体差异并配套回归测试。
- 保留 `/ws` 及 `price_update`、`alert`、`pong`、`config_update` 等已有消息契约。
- 保留 `gold-monitor` 命令和 `gold_monitor.web:app` 启动入口。现有 `from gold_monitor.web import app, db` 使用点需逐项迁移，并明确 `web.db` 的过渡或废弃方案，避免为兼容重新引入导入时数据库初始化。
- 保留现有环境变量、数据库数据及 LLM 配置文件的可读取能力。改变持久化格式必须有迁移、失败处理和回退方案。
- 保留 Mock 模式、模型搜索失败时的降级标记、来源信息，以及脱敏密钥不覆盖原值的行为。
- 保留使用尚未保存的模型表单配置探测连接和模型列表的能力。
- 数据源只能提供当前价格时，补间隙仍只新增当前样本，不生成或伪造历史报价。
- 已明确列出的缺陷不作为必须保留的兼容行为；修复应与结构调整分开提交。

## 4. 目标职责划分

| 边界 | 负责内容 | 依赖方向 |
|------|----------|----------|
| 应用装配与运行资源 | 配置加载、创建服务、启动与关闭、任务归属 | 在入口创建并连接各组件 |
| API 路由 | 请求校验、权限依赖、服务调用、响应转换 | 调用业务服务 |
| 业务服务 | 采集流程、告警流程、通知配置生效、分析与缓存策略 | 调用规则、存储和外部适配器 |
| 规则与数据对象 | 去重规则、告警规则、单位换算、报价及处理结果 | 尽量保持纯逻辑，不依赖 FastAPI 或网络 |
| 存储模块 | 查询、事务、数据保存、配置文件写入 | 管理数据库会话和文件操作 |
| 外部适配器 | 行情源、模型 SDK、搜索、通知渠道 | 明确超时、异常和关闭契约 |
| 前端模块 | API client、状态更新、图表、行情、告警、分析、设置 | 通过统一请求与状态更新入口协作 |

目录和类名在相应阶段确定，优先围绕实际职责抽取。避免把原来的所有全局状态原样搬进一个新的大对象，或为每个简单函数增加抽象层。

## 7. 提交、验收与回退方式

1. 从快照基线继续工作；实施时建立 `codex/` 前缀的重构分支，保持阶段范围可审查。
2. 每阶段按依赖、模块抽取、行为修复划分小提交。每个提交说明改动目的和验证结果，避免全项目格式化掩盖业务差异。
3. 每阶段结束运行对应测试并核对契约；不在已知回归未处理时扩大改动范围。测试失败须区分原有失败、环境问题和新回归。
4. 代码回退优先采用可审查的反向提交，不覆盖其他未提交工作；数据格式变化按独立迁移方案处理，不能假定回退代码会回退数据库。
5. 第一批建议实施阶段 0–1，验收测试基础和资源管理后，再推进采集、告警及分析模块。
